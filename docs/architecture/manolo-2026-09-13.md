# Manolo: lectura del sistema al 13/09/2026

[Diagrama interactivo](manolo-2026-09-13.html) · [Especificación editable](manolo-2026-09-13.architecture.json)

El sistema sigue siendo híbrido. El Worker de Cloudflare recibe los mensajes de Meta, carga contexto desde D1, interpreta texto/audio/imágenes, resuelve el rol del contacto y coordina las operaciones. D1 sigue siendo la base principal de conversaciones, deduplicación y estados de los roles. La escritura en sombra de mensajes hacia PostgreSQL no cambia esa autoridad.

La ruta verde del diagrama representa la facturación: usuario → Meta → Worker → Caddy y bridge Node → FacturaYa → SUNAT. No todos los mensajes recorren esa ruta completa: primero se recopilan datos y se muestra el borrador; la emisión requiere confirmación del usuario. La respuesta y el PDF vuelven a WhatsApp a través del bridge, Worker y Meta.

El bridge autoriza empresa, contacto, permiso y sesión antes de usar el token de FacturaYa. Worker → VPS usa HTTPS, HMAC, timestamp y request ID; los tokens empresariales permanecen en el VPS. PostgreSQL conserva roles, membresías, empresas, sesiones de acceso a FacturaYa, solicitudes idempotentes y auditoría. La TUI administra esos datos por SSH; su flecha no implica un puerto público de PostgreSQL.

Los roles registrados son chat (`cat`), cotizaciones (`quotes`), Print Advisor, tienda y asesor empresarial. Groq y el proveedor compatible con OpenAI aportan inferencia; no son las fuentes de verdad de permisos, importes emitidos ni estados de SUNAT. R2 guarda documentos temporales y Browser Run genera PDF de cotizaciones; el PDF fiscal corresponde a FacturaYa.

Para conservar once componentes, se agruparon Caddy y el bridge, y R2 y Browser Run. Las dependencias secundarias de Print System y tienda se describen aquí: Print Advisor consulta el bridge/PostgreSQL con fallback D1; tienda usa su API externa firmada y sigue fuera del alcance de migración al VPS. La landing Astro tiene un despliegue independiente y no recibe el webhook de WhatsApp.

## Diferencia con la documentación histórica

Aunque `docs/project/status.md` afirma que se retiraron los handlers financieros, el código consultado conserva `FinanceRoleHandler`, el modo `finance` de `enterprise-advisor` y `createFinanceRepository(env.NEON_DATABASE_URL)`. Es evidencia de integración presente en código; su disponibilidad real depende de la configuración desplegada. Esta nota no reactiva ni modifica ese código.

Actualización 2026-09-13: el mismo día se eliminó ese código — rol `finance`, adaptador Neon, contrato `FinanceRepository`, composición en `src/index.ts`, secreto `NEON_DATABASE_URL`, dependencia `@neondatabase/serverless` y modo `finance` de `enterprise-advisor`. La observación anterior describe el estado previo al recorte.

La corrección del nombre opcional sin DNI está presente en el código local de Manolo. Su presencia local no prueba cuál revisión está atendiendo mensajes en producción.
